# workflow-find — decision log

## Session 2026-10-13 — governance verdict

Origin: **USER-REQUESTED** (Ben, project thread "Making Workflow installable
without contributor access": "have claude defer to its tools automatically,
maybe have an easy way for it to search through the tool to know if to use it").
Built on a branch and held for the requester's review.

- **Weakness:** a plugin user only sees the descriptions of the plugins they
  installed. With workflow-core alone (the recommended install), ~130 public
  skills are invisible, so Claude cannot know a fitting skill exists; with
  workflow-full every description sits in context permanently.
- **Not already covered:** `bmad-help` routes BMAD phases inside an adopted
  project; `workflow-start` onboards a repo; `wf map` / `wf describe` index the
  user's project, not the toolset; `docs/tool-usage-map.md` is hand-written and
  private. Nothing searches the toolset itself from a plugin install.
- **Why a skill, not a script alone:** the search must be reachable from a
  plugin install with no repo checkout, and only a skill's description puts it
  in front of Claude at the moment of choice. The ranking itself is a stdlib
  script (`scripts/find.py`), so the skill stays a thin instruction layer.
- **Verdict:** CREATE-NEW, shipped in workflow-core (and workflow-full, which is
  self-sufficient on web). The catalog is a BUILD output of `wf plugin build`,
  derived from the same resolved plugin set the leak gate enforces, so it can
  only ever list public skills; `wf plugin --check` verifies it.

## Validation

- Live-scan ranking spot-checked in-repo (PRD, brainstorm, 3D print, code
  review, Playwright, edge cases, architect, novel chapter → expected skill in
  the top 3; an off-domain query returns little or nothing).
- Trigger + artifact evals authored (`evals/`); a hermetic `bmad-eval-runner`
  run is still pending a Docker + key box.
