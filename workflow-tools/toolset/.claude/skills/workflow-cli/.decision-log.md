# workflow-cli — decision log

## Session 2026-10-13 — governance verdict

Origin: **USER-REQUESTED** (Ben, 2026-10-13: "the wf commands should go
public"). Ships with the new `workflow-tools` plugin, which puts `wf` on PATH.

- **Weakness:** a plugin user who installs workflow-tools gets a `wf` binary but
  no way for Claude to know which tool fits which job; the README and
  `docs/tool-usage-map.md` that explain it are in the private repo.
- **Why a skill:** only a skill description reaches Claude at the moment of
  choice from a plugin install. Kept to a job-to-command table plus the
  read-only vs. write rules; per-command detail stays in each tool's `--help`.
- **Verdict:** CREATE-NEW, public in workflow-tools and workflow-full.

## Validation

- Built workflow-tools and ran `wf help`, `start`, `map build/query`,
  `describe`, `memory init`, `spec init`, `browse status`, `guard status` from a
  fresh project outside the repo; all wrote into the project, none into the
  plugin dir; an unshipped command (`deploy`) refused with a clear message.
- Trigger + artifact evals authored; hermetic eval-runner run pending.
